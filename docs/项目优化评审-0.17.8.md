# 听匣 0.17.8 项目优化评审

评审日期：2026-10-26。代码基线：`410ba9d`；应用版本：`0.17.8`。

本报告前面的证据描述修复前的状态；本轮修复与验证记录见文末“0.17.9 修复落地”。

**结论：还有明显的优化空间。下一轮收益最高的是统一播放时间与异步状态、完善离线和恢复流程，再围绕续听、睡前收听、书架整理增加功能。**

## 1. 评审范围与证据

本次检查了 Android 播放服务、控制器、Room 数据与迁移、导入与重扫、备份、在线接口、主要 Compose 页面，以及 Python 音频流服务。

证据分三类：

- **代码确认**：能从当前调用链明确判断的问题；涉及设备行为的最终表现仍需集成测试。
- **执行复现**：直接调用当前 Python 服务代码，在临时目录、模拟上游条件下复现。
- **待设备验证**：由布局与状态实现推断的体验风险，尚未在手机上测量。

验证结果：

- 当前源码中的进度写入、下载取消、下载任务切换、章节裁剪、播放反馈共 **35 个既有 JVM 测试通过**。使用缓存中的 Kotlin 2.0.21 编译器和项目对应依赖重新编译这些源码，在临时目录运行 JUnit；未使用旧编译结果替代当前源码。
- 音频流服务的普通 Range、后缀 Range、越界 Range 路径已执行检查；缓存预算边界已复现。
- `./gradlew testDebugUnitTest --console=plain` 在 AAPT2 阶段失败：当前主机为 aarch64，所需工具的运行库缺失，报 `libdl.so.2`。ADB 也无法启动，因此本次没有完成完整 Gradle 测试、模拟器测试或界面截图验证。
- 没有修改应用业务代码、没有请求在线上游。此报告不把 UI 风险描述为已测得的卡顿或已复现的崩溃。

## 2. 已经做好的部分

目前不是功能薄弱的播放器，已有本地/在线导入、M4B 内嵌章节解析、后台播放、书签、逐书设置、睡眠定时、章节筛选与批量操作、TTS、追更、声文同步、桌面组件、备份和收听统计。

值得保留的实现包括：

- 进度通过 `ProgressWriter` 串行保存，并处理销毁时的最终写入。
- 重扫保留章节身份，使用事务处理章节顺序变化，并在应用前与播放服务建立写入屏障。
- 下载取消会传递给底层 `CacheWriter`；批量任务切换等待前一任务清理。
- 缓存徽标按真实磁盘状态校正，按音色区分缓存身份。
- 正文在真人版时间轴不可信时退回普通阅读，避免显示错误高亮。
- 章节列表采用逐行惰性渲染与分组定位，书架查询已有防抖。

这些能力不需要重复开发。重点是把它们之间尚未统一的契约补齐。

## 3. 优先修复的内部逻辑

这里的 P1 表示建议优先安排在下一轮稳定性修复；P2 表示随后完善。不是线上故障等级。

### R1 · P1：播放相对时间、源录音时间与章节时长混用

**代码确认。** Media3 的播放位置和时长属于裁剪后的窗口，而正文时间点和原始录音时长属于源录音。当前几个调用直接把这些数值互相使用。

- `PlaybackService.kt` L369–375 将 `player.duration` 写入在线章节时长。
- `BookRepository.kt` L294–312 和 `Daos.kt` L325–326 只在原时长未知时写入，之后不会纠正。
- `PlayerTextPage.kt` L82–86 用播放器相对位置匹配原始句子时间；L207 直接将句子原始时间传入 seek。
- `PlayerViewModel.kt` L302–308 直接把当前相对位置存成书签；`setSkipOffsets` 只映射正在播放的位置，没有映射已有书签。
- `PlayerController.kt` L883–887 用原章节时长累加整书偏移，再加裁剪后的当前位置。

具体影响：

1. 在线章节第一次播放时，原时长未知且已设置跳过 30 秒片头，900 秒录音的裁剪时长约为 870 秒。把 870 秒存为原时长，后续重建队列再减片头，窗口可能进一步缩短。
2. 跳过 30 秒片头后，播放页显示 2:00，实际源录音已到 2:30；正文高亮会错开 30 秒。点原时间轴的 3:00，会跳到源录音约 3:30。
3. 开着跳过片头保存书签后，再关闭片头跳过，书签会回到另一个时间点。
4. 整书剩余时间使用原始章节总和，不能准确表达跳过片头片尾后的实际所需时间。

建议：明确三种时间的边界：源录音时间、章节内时间、当前裁剪窗口时间。进度和书签保存稳定坐标，UI 与 Media3 边界通过现有 `clipRelativeToAbsolute` / `absoluteToClipRelative` 转换；M4B 需保留章节窗口起点。原时长从可信元数据获取，禁止直接写入裁剪后的 `player.duration`。

修复应包含旧数据兼容：历史书签没有保存创建时的裁剪窗口，不能凭当前设置保证全部自动还原。需要定义迁移规则与可修正入口。

验收：跳过片头前后，同一书签仍指向同一句；TTS 点句子与高亮对应实际声音；未知时长首次播放、重建队列后时长稳定；M4B 场景也成立。

### R2 · P1：正文请求缺少章节与音色身份校验

**代码确认。** `PlayerViewModel.kt` L81–119 中，已有请求加载时直接退出；加载成功后直接写回，没有校验当前章。`FullPlayerScreen.kt` L156–157 只在页码、正文可用性或章节 ID 改变时请求正文。

典型过程：A 章正文尚未返回 → 用户切到 B 章 → B 因 `current.loading` 而不发起请求 → A 返回后显示 A 正文。此时请求完成没有改变触发条件，B 不一定补加载。

此外，同一章出错后 `ensureChapterText` 因已有 error 而跳过，正文页没有直接重试按钮；换音色后章节 ID 不变，旧音色时间轴也可能继续显示。Repository 的缓存键已经包含 tone，但 ViewModel 的有效身份未包含 tone。

建议：以 `(bookId, chapterId, toneId)` 作为请求身份，切换时取消旧任务；结果提交前再校验身份。正文页提供重试，恢复网络后允许重新加载；换音色时明确失效旧时间轴。

验收：人为延迟 A 请求，连续切 B/C，只显示 C；同章换音色重新获取时间轴；加载失败可在原页重试。

### R3 · P1：倍速面板“全局”含义与保存行为不一致

**代码确认。** `PlayerSheets.kt` L130–149 的“全局”点击调用 `onUseGlobalSpeed`，实际含义是“恢复全局默认”；随后选择任意倍速仍调用同一个 `onSpeedSelected`。`PlayerViewModel.kt` L181 总是以 `asBookDefault = true` 保存。

因此用户选“全局”再选 1.5x，最终仍为当前书创建 1.5x 覆盖，不会把 1.5x 保存为全局默认。“本书”选项自身也没有切换范围的动作。

建议：把“修改范围”与“继承默认”分开：选择本书/全局是面板状态，提交速度时带上范围；“恢复全局默认”单独提供操作。面板明确显示当前全局默认值。

验收：修改全局后，新书继承该值；有独立设置的书继续使用自身设置；恢复默认后本书覆盖为空。

### R4 · P1：在线搜索把输入框内容当成分页查询身份

**代码确认。** `ShelfViewModel.kt` L185 从 `_fqQuery` 取分页关键词，而 L212–214 每次输入都会修改它；`fqSearchId` / `fqPage` 仍属于上一次已提交搜索。

即使没有并发，也存在问题：搜索 A → 输入框改成 B、尚未提交 → 点“加载更多”，会用 B 与 A 的分页状态请求，并追加进 A 的结果。

另有并发风险：搜索、加载更多、选择书籍的协程没有 request ID 或旧任务取消。键盘搜索入口 `FqNovelSheet.kt` L223 没有限制 loading，旧结果可能覆盖新结果；选书的音色请求也需要同样的身份隔离。

建议：分开 `inputQuery` 与 `activeSearchQuery`，分页状态与搜索身份放入同一个状态对象；新搜索取消旧搜索和分页，结果按身份校验后提交。发现页首次失败后也应允许刷新，当前 `fqDiscoverLoaded` 在请求前置 true，会让失败状态持续到 ViewModel 重建。

验收：输入未提交的新词不影响旧结果分页；旧请求晚返回不覆盖新结果；失败后原页可重试。

### R5 · P1：恢复备份没有接入播放变更屏障

**代码确认。** `SettingsViewModel.kt` L83–90 直接导入备份；`BackupRepository.kt` L185–240 覆盖已有书进度并删除、重建书签，未协调正在运行的播放服务。`PlaybackService.kt` L295–302 仍每 5 秒保存当前位置。

正在听书时恢复历史备份，数据库里的恢复位置可能很快被旧队列的当前位置覆盖；章节标题、音色、跳过设置也没有统一刷新到当前队列。重扫已有屏障，但恢复未复用。

另外，选中文件后立即恢复，界面未展示会覆盖哪些现有数据。备份旧于当前书签时，后来新增的书签会被删除，这一“覆盖恢复”行为需要向用户明确呈现。

建议：解析与预览 → 选择覆盖/合并规则 → 暂停并清空旧队列、等待进度写入屏障 → 恢复事务 → 失效派生缓存并重建队列。明确恢复后的播放状态；数据库与 DataStore 分别提交，需要处理部分成功的结果。导出也应使用一致的数据库快照。

备份完整性还可提升：当前未携带实际收听统计、在线元数据同步来源、部分远端事实；手动封面保存为应用私有文件，导出只保留 content/http URI，因此迁移到新设备会失去该封面。在线信息来源丢失还会影响本地书正文关联与“清除在线信息”的能力。

`importFrom` 使用 `InputStream.available()` 判断大小，不能保证限制实际读取字节；建议改为累计字节限制，避免正常大备份或 provider 流造成内存问题。

### R6 · P1/P2：实际收听统计边界不准确，记录量持续增长

**代码确认。** `PlaybackService.kt` L429–445 仅在 5 秒轮询时判定播放状态，没有在暂停、恢复、缓冲和切书事件上结算区间。

- 首次播放到下一次轮询之前的时间可能漏记。
- 两次轮询间的短暂停若未被采样，会被算入收听时间。
- 两次轮询间切书，整个区间可能记给新书。
- 最后一次轮询到暂停/销毁之间的尾段可能漏记。

建议：使用单调时钟，在 `isPlaying` 状态变化、书籍切换与退出时结算区间；轮询仅用于定期落盘。

存储方面，`StatsRepository.kt` L53 每次区间插入一行。每天听 2 小时，一年约新增 **525,600 行**；现在页面只需要每天、每本书的汇总。建议按 `(bookId, localDate)` 累加，必要时保留有限期明细。`dayEnd = dayStart + 24h` 在夏令时切换日不成立，应按当地下一日零点分段。

### R7 · P2：追更失败会占用成功检查的间隔

**代码确认。** `OnlineUpdateChecker.kt` L60–70 在检查前保存 `lastUpdateSweepAt`。离线启动时，即便所有检查失败，仍可能进入 6 小时等待；在线恢复后不会立即自动补查。

TTS 路径不取音频 meta，`applyRemoteUpdate` 的完结状态沿用旧值，因此小说从连载转完结的事实没有在这条路径刷新。新增章节还仅按已有 item ID 过滤，建议对本次返回列表也 `distinctBy(itemId)`，并明确处理中途补章、上游目录修订的规则。

建议：区分最后尝试与最后成功检查；失败退避、网络恢复后补查；按书记录结果并保留可见的最近检查状态。TTS 从小说信息接口刷新完结状态。

## 4. 离线与服务端

### R8 · P1/P2：离线下载与临时播放缓存共用 LRU

**代码确认的产品限制。** `CacheManager.kt` L53–54、L159：文件位于 `cacheDir`，所有录音共用固定 1 GiB LRU。用户主动缓存整本书，与播放产生的临时缓存受同样淘汰规则；系统清缓存也会影响它。

例如一本书超过 1 GiB，下载后半本时可以淘汰前半本；“全部缓存任务完成”不等于整本书始终可离线播放。0.17.8 已修正徽标一致性，但还没有提供持久离线的产品保障。

建议：明确区分临时缓存与用户保留的下载。主动下载采用受保护的存储/淘汰策略，用户可设置容量；容量不足应呈现预计占用与可选章节范围。下载中心持久化任务，支持暂停、继续、失败重试、仅 Wi-Fi，并显示“已完成下载”与“当前仍可离线”的实际状态。

`PrefetchService` 当前更换批量任务会替换前一任务，状态保存在内存中；多个书籍排队下载和进程回收后继续是新增能力。

### R9 · P2：本地权限探测仍可能阻塞主线程

**代码确认。** `PlayerController.playBook` 由 ViewModel 主线程调用，直接进入 `BookRepository.checkBookAccess`；后者调用同步的 `contentResolver.query`。多文件导入还会逐个验证所有章节 URI。

目录 provider 慢、书籍文件多时，一次播放可能等待大量查询。建议将权限与文件探测整体移到 IO，区分目录权限失效和某个文件丢失；当前目标章检查优先，其余源完整性通过后台索引检查完成。

缓存同步每次会读取全部在线章节，并逐项检查完整性；大书架中应基于受影响的缓存 key 增量同步，重启/显式清理时再全量校正。先测量 100 本书、1,000/10,000 章数据，不能仅凭代码行数推断实际卡顿。

### R10 · P2：音频流服务的预算与并发边界

**执行复现。** 对当前 `prepare_chapter` 模拟上游并生成 10 字节录音，将缓存预算设置为 5 字节。L239 调用预算清理后，函数返回的 target 已不存在，后续 `serve_file` 会失败。

实际服务默认预算为 20 GiB，因此此边界更可能在自定义小预算时触发。多个不同章节同时准备时，也存在另一任务清理文件与当前请求打开文件之间的竞争窗口。

建议：保护准备中和正在发送的文件，明确超过预算的单文件策略；先取得可用文件句柄，再发送响应；清理与准备共享有效的生命周期规则。

其他扩展项：HTTP 请求线程没有全局准备并发上限；`warm_pool` 只限制 worker 数，队列未限制；章节锁字典没有回收。多用户部署时，应限制准备并发与排队长度，对正在播放请求给出更高优先级，并清理闲置锁。

Range 正常与越界路径已执行。额外发现 `Range: bytes=-` 被当作整文件返回 206，建议修正空范围解析并补协议边界检查。服务端测试目前未接入 Android CI。

无障碍建议对实际可点击区域与语义逐项测试。部分按钮视觉尺寸为 28/40/44dp，Compose 可能扩展命中区域，不能只凭视觉尺寸认定触控不合格；应检查扩展后是否重叠、TalkBack 是否能正确解释当前状态，以及长按是否可发现。

设备验收至少覆盖：窄屏手机、普通手机、横屏/分屏、大字体 1.5× 与 2×、深浅主题、亮色封面、TalkBack。验证控件可见与可操作，再决定动画、模糊和装饰层的取舍。

## 7. 架构调整方式

目前 `BookRepository` 约 1,143 行、`PlayerController` 981 行、`BookDetailViewModel` 784 行、`BookDetailScreen` 1,399 行，说明职责已集中到少数文件。文件长度不是性能证据，但会增加修改一个行为时漏掉其他路径的概率。

建议沿本轮问题逐步拆分：

1. 播放时间映射与展示计算形成独立策略，播放器、正文、书签、恢复共同调用。
2. 播放库变更流程统一为协调入口，重扫、恢复、换音色、跳过设置走一致的暂停/屏障/刷新规则。
3. 在线搜索、音色选择、正文请求各自使用可辨认的状态与请求身份；长期偏好与临时页面状态分开。
4. 本地导入/重扫、在线目录/录音、元数据编辑、备份各自归集职责；暂时没有必要全面改成多个 Gradle 模块。
5. 网络请求支持底层取消、错误分类与有界读取。`runCatching` / `catch(Exception)` 在协程中显式传播 CancellationException，避免取消后仍退回普通文本或更新旧状态。
6. 下载存储和临时缓存分开定义生命周期；统计使用事件结算与日汇总。

不要以“统一”重新增加多个进度写入者。PlaybackService 继续保持播放进度权威，其他流程通过明确的变更契约协调。

## 8. 推荐实施顺序与验收

| 阶段 | 范围 | 完成标准 |
|---|---|---|
| A：稳定性 | R1 时间/时长、R2 正文、R3 倍速、R4 搜索、R5 恢复 | 当前源码问题有失败用例，修复后通过；设备验证跨功能定位一致；备份恢复不被旧队列覆盖 |
| B：体验一致性 | 定时交互、返回关闭浮层、小屏与大字体、偏好保存、时间和徽标语义；R6/R7 | 同一设置在不同页面含义一致；所有关键控件在验收尺寸可操作；统计与追更失败边界可验证 |
| C：常用增强 | 智能回退、跳转撤销、睡前记录、下载中心；R8–R10 | 离线可用状态可信、下载中断可继续、用户能恢复误操作和昨晚收听位置 |
| D：扩展 | 分组、音色试听、完整备份、正文离线/搜索 | 依据实际使用反馈确定范围，避免多个大型功能同时上线 |

最值得补的测试是跨功能契约：

- 未知在线时长 × 跳过片头片尾 × 二次播放。
- 保存书签 × 改跳过设置 × M4B 与普通录音。
- 正文慢请求 × 连续切章 × 同章换音色 × 失败重试。
- 改输入词未提交 × 加载更多 × 新旧请求倒序完成。
- 正在播放 × 备份恢复 × 旧进度写入屏障。
- 播放/暂停/缓冲/切书 × 统计结算；当地夏令时跨日。
- 下载超过容量 × 淘汰 × 音色切换 × 进程重建。
- 小屏、大字体、TalkBack 下的播放器与浮层。

现有纯策略测试已经覆盖了不少局部边界；下一轮主要补充组件之间的关系，避免继续出现“各自正确、连在一起偏移”的问题。
